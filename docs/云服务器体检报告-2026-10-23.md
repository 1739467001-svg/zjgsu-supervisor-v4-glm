### 待处理（按优先级分级）

**P1（建议尽快决策）**

1. **SSH 允许 root 密码登录**（PermitRootLogin yes + PasswordAuthentication yes），24 小时内 57 次失败登录尝试——公网机器正在被持续爆破。处置：改为密钥登录并关闭密码认证。**注意：改错会导致你被锁在服务器外，需先放好密钥再切换，建议由我在一次会话内完成。**
2. **2 个 critical 级依赖漏洞**（含 dompurify 3.3.0，pnpm audit 检出 101 项中最高危的两项）。处置：升级 dompurify 等直连依赖（一行 pnpm up），本地跑通测试再零构建发版。**收益是堵住 XSS 供应链风险，风险是升级可能引入行为变化，需回归测试把关。**

**P2（择机集中处理，建议放到学校迁移前）**

3. 101 项依赖漏洞总盘子（绝大多数是低危的传递依赖）：随 P1-2 顺带处理，或在学校迁移前集中做一次 `pnpm up --patch-level`。
4. 89 个系统包待更新（apt 安全更新）：低峰期执行 `apt upgrade`，重启 drcopilot 相关容器（本系统容器不受影响）。
5. 登录接口无失败次数限制 / 无验证码：校内迁移后内网部署时该风险自然大幅降低。

**P3（增强项，不阻塞长期运行）**

6. OAuth（GitHub）未配置——属可选功能，缺省不影响使用。
7. 进程信号处理（SIGTERM/SIGHUP）：当前靠 Docker restart 自愈兜底（已实测 20 秒恢复），增强属锦上添花。
8. `dnf`/`apt` 等 25 个 SUID 二进制：属 Ubuntu 默认态，单用户管理机可接受。

### 迁移步骤（约 1.5 小时，照《数字办部署执行清单》执行）

1. **前置确认（需向数字办索取）**：SSH 账号、资源规格、开放端口、域名与证书方式。目标 Ubuntu 22.04+、4 核 8G（按申请）。
2. **装底座（约 30 分钟）**：Docker + Nginx；时区 Asia/Shanghai。注意学校内网若无法直连 ECR 镜像源，需要换成学校镜像源或提前导入镜像 tar（本地已验证 docker.1ms.run 可拉 mysql:8.0 / node:22-alpine）。
3. **零构建上线（约 30 分钟）**：按 DEPLOY.md 流程——本地构建 → tar 上传 → 解压运行。**严禁在学校服务器上执行 docker compose build / pnpm install**（2 核 2G 教训，学校机器配置更高风险等价）。`VITE_BASE_PATH` 需按学校域名/路径重新构建（构建期注入，不可运行时改）。
4. **数据迁移（约 20 分钟）**：停写 → 服务器最终备份 → 恢复到新库 → 逐表核对（users 101 / courses 4101 / evals 81 / plans 57 / semesters 2）→ 恢复业务。
5. **密钥全部新生成**：JWT_SECRET、DB root 密码、数据库密码全部换新，**严禁复用旧值**。
6. **验收（约 10 分钟）**：五角色抽验 + 学期切换 + /login 短地址跳转 + 统计口径对账（按《数字办部署执行清单》第五节）。
7. **收尾**：迁移成功后保留旧服务器 2 周（只读观察），再释放资源。

### 迁移风险点

- **镜像源**：ECR 在校内网不可达的概率高，备选 docker.1ms.run（已验证）或镜像 tar 导入。
- **BASE_PATH 重构建**：如学校用根路径部署则改动为零；用子路径则必须本地重构建产物。
- **小内存机器**：若学校给的虚拟机同样 ≤4G，务必延续零构建流程，否则重演两次压垮事故。
- **旧密钥处置**：迁移完成后旧 JWT_SECRET 应作废（用户需重新登录一次，属预期）。
